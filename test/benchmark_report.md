| 项目 | 配置 |
|---|---|
| **操作系统** | Linux |
| **编译器** | GCC |
| **服务器线程** | 16 Worker + 1 Main Thread |
| **测试工具** | wrk2 (HTTP 基准测试) |
| **测试接口** | HTTP GET "/" 返回 "Hello World" |
| **测试地址** | http://127.0.0.1:8080/ |

## 二、测试方法学

### 2.1 为什么选择 wrk2

| 工具 | 特点 | 选择理由 |
|---|---|---|
| **wrk** | 尽力发送，无速率控制 | 测出最大吞吐，但延迟失真 |
| **wrk2** | 支持 `-R` 恒定速率节流 | 测出真实延迟分布（P99 可信） |

**核心区别**：wrk2 的 `-R` 参数让客户端按目标速率节流，模拟真实生产负载下的延迟表现，而非客户端开足马力压垮服务器。

### 2.2 测试参数说明

```bash
wrk -t <客户端线程数> -c <连接数> -d <时长> -R <目标RPS> -L --timeout=3s http://...
```

| 参数 | 取值 | 含义 | 选择理由 |
|---|---|---|---|
| `-t` | 16 | 客户端线程数 | 不超过客户端 CPU 核数，避免上下文切换污染延迟 |
| `-c` | 800~50000 | 并发连接数 | 分档测试，从低并发到高并发逐步加压 |
| `-d` | 30s~120s | 测试时长 | 足够让系统进入稳态，避免冷启动噪声 |
| `-R` | 500000 | 目标 RPS | 恒定速率节流，模拟真实生产负载 |
| `-L` | (开关) | 启用延迟分位统计 | 获取 P50/P90/P99/P99.9 等关键指标 |

### 2.3 测试策略

1. **稳态测试**：直接跑 30 秒以上，而非 1 秒循环
   - ❌ 错误做法：1 秒循环 120 次（每次重建连接，永远无法进入稳态）
   - ✅ 正确做法：连续跑 30 秒+（连接复用，系统预热，数据真实）

2. **维度 1：时间稳定性**
   - 30 秒测试：验证短期性能
   - 5 分钟测试：验证长期稳定性，观察尾部延迟漂移

3. **维度 2：连接数容量**
   - 分档测试：800 → 2K → 5K → 10K → 20K → 50K
   - 保持 RPS 50 万不变，观察性能退化曲线

## 三、压测结果汇总

### 3.1 稳态性能测试（50 万 RPS，800 连接）

| 指标 | 30 秒测试 | 5 分钟测试 | 状态 |
|---|---|---|---|
| **总请求数** | 14,854,015 | 149,826,089 | — |
| **QPS** | **495,167** | **499,424** | ✅ 稳定 |
| **P50** | 1.20ms | 1.20ms | ✅ 稳定 |
| **P75** | 1.69ms | 1.69ms | ✅ 稳定 |
| **P90** | 2.11ms | 2.11ms | ✅ 稳定 |
| **P99** | **2.87ms** | **2.94ms** | ✅ 稳定 |
| **P99.9** | 3.75ms | 19.01ms | ⚠️ 升高 |
| **P99.99** | 5.04ms | 52.22ms | ⚠️ 升高 |
| **Max** | 12.14ms | 107.52ms | ⚠️ 升高 |

**结论**：
- 核心性能（QPS + P99）在 5 分钟内完全稳定
- 尾部延迟（P99.9+）升高是长时间运行的正常现象
- 根因：CPU 调度抖动、内存碎片累积、偶发锁竞争

## 四、关键性能指标总结

### 4.1 核心能力

| 维度 | 数值 | 说明 |
|---|---|---|
| **稳定 QPS** | **49.9 万/秒** | 16 线程配置下的持续稳定吞吐 |
| **P99 延迟** | **2.94ms** | 99% 的请求在 3ms 内完成 |
| **最大稳定连接数** | **1~2 万** | 超过 2 万后延迟显著恶化 |
| **过载连接数** | **5 万** | 服务器完全无法处理，QPS 暴跌 45% |

### 4.2 性能区间划分

| 区间 | 连接数 | QPS 保持率 | P99 延迟 | 业务可用性 |
|---|---|---|---|---|
| **舒适区** | 800 ~ 10K | > 98% | < 10ms | 完全可用 |
| **临界区** | 10K ~ 20K | > 97% | 10~25ms | 可接受，需监控 |
| **过载区** | > 20K | < 95% | > 25ms | 不可用，需扩容 |

### 4.3 优化效果对比

| 优化项 | 改造前 | 改造后 | 提升 |
|---|---|---|---|
| **全局时间轮 → 局部时间轮** | 16 线程 QPS 6 万 | 16 线程 QPS 65 万 | **10.8 倍** |
| **移除 stdout 日志** | QPS 18 万 | QPS 27 万 | **50%** |
| **简化 HTTP 协议** | QPS 45 万 | QPS 54 万 | **20%** |

## 六、面试可用性能总结

### 6.1 一句话电梯演讲

> "我开发的 C++ 高并发 Web 服务器基于 epoll ET + 多 Reactor 架构，16 线程配置下稳定 QPS 50 万，P99 延迟 3ms，可支撑 1~2 万并发连接。核心优化包括全局时间轮改局部时间轮（10 倍性能提升）、日志异步化、连接池复用。"

### 6.2 详细性能描述（面试版）

> **QPS 吞吐**：在 16 Worker 线程配置下，稳定 QPS 达到 **49.9 万/秒**（5 分钟持续压测验证）。这意味着每秒处理近 50 万次 HTTP 请求，每个请求处理耗时约 2 微秒。
>
> **延迟分布**：P50 为 1.2ms（半数请求在 1.2ms 内完成），P99 为 2.94ms（99% 的请求在 3ms 内完成），即使在 50 万 QPS 的高压下，99.9% 的请求也能在 20ms 内响应。
>
> **并发能力**：服务器可稳定支撑 **1~2 万并发连接**，在此范围内 QPS 保持率 > 97%，P99 延迟 < 25ms。超过 2 万连接后性能显著下降，5 万连接时 QPS 暴跌 45%。
>
> **稳定性**：5 分钟持续压测显示核心性能（QPS + P99）完全稳定，仅尾部延迟（P99.9+）因 CPU 调度抖动略有升高，属于高并发系统的正常现象。

### 6.3 架构亮点（面试版）

> **技术栈**：C++17 + Linux epoll + 多线程 + 时间轮
>
> **核心特性**：
> 1. **epoll ET 边缘触发**：减少内核态/用户态切换开销
> 2. **多 Reactor + Worker 池**：主线程分发，Worker 线程处理 IO
> 3. **局部时间轮超时管理**：每个 Worker 独立持有时间轮实例，消除全局锁竞争
> 4. **连接池复用**：预分配 Connection 对象，避免热路径内存分配
> 5. **异步日志系统**：生产者-消费者模型，业务线程只入队不写盘
>
> **优化成果**：
> - 全局时间轮 → 局部时间轮：16 线程 QPS 从 6 万提升至 65 万（**10.8 倍**）
> - 移除 stdout 日志：QPS 提升 50%
> - 简化协议解析：QPS 提升 20%

### 6.4 已知瓶颈与优化方向

> **当前瓶颈**：
> 1. **主线程 accept 单点**：单 Reactor 架构下主线程 accept 成为瓶颈，36 线程性能反而下降
> 2. **连接容量上限**：超过 2 万连接后，epoll 单次返回事件过多，Worker 处理不及时
>
> **优化方向**：
> 1. **SO_REUSEPORT 多 Reactor**：每个 Worker 独立 listen + accept，消除主线程单点
> 2. **epoll 批量处理分片**：每轮只处理 N 个事件，让出 CPU 给其他逻辑
> 3. **IO 线程池**：Worker 只负责事件分发，具体 IO 操作交给独立线程池

## 七、测试方法论反思

### 7.1 测试时长的选择原则

| 时长 | 适用场景 | 注意事项 |
|---|---|---|
| 1~5 秒 | 快速探测 | 数据不稳定，仅用于验证服务存活 |
| 10~30 秒 | 找拐点、比档位 | wrk2 推荐下限，足够让系统预热 |
| 1~5 分钟 | 验证稳态 | 能暴露尾部延迟漂移、内存泄漏 |
| 10 分钟+ | 长期稳定性 | 发现 CPU 调度周期、缓存淘汰等长周期问题 |

### 7.2 测试参数的选择原则

| 参数 | 选择原则 | 错误做法 |
|---|---|---|
| `-t` (线程数) | ≤ 客户端 CPU 核数 | 设成 64+ 导致上下文切换污染 |
| `-c` (连接数) | 分档测试，覆盖 2 个数量级 | 只测 1 档或 1 个连接数 |
| `-d` (时长) | ≥ 30 秒 | 用 1 秒循环（无法进入稳态） |
| `-R` (速率) | 恒定速率节流 | 不用 `-R`（测不出真实延迟） |

### 7.3 避免的测试陷阱

| 陷阱 | 描述 | 正确做法 |
|---|---|---|
| **1 秒循环** | 每次 1 秒测试都重建连接，永远无法进入稳态 | 直接跑 30 秒+ |
| **只测 1 档** | 只测 800 连接，不知道容量上限 | 分档测试连接数 |
| **不看尾部** | 只看 P99，忽略 P99.9 和 Max | 关注完整分位表 |
| **单次测试** | 跑一次就下结论 | 至少跑 3 次取平均 |
