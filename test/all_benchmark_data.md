# TinyWebServer 全量压测数据汇总

> **生成时间**：2026-08-17  
> **测试工具**：wrk2 (Coordinated Omission Rate Limiter)  
> **测试协议**：HTTP/1.1 (长连接)  
> **测试目标**：http://127.0.0.1:8080/  
> **硬件环境**：双路 Intel Xeon Gold 5220 @ 2.20GHz / 36 物理核 / 283GB 内存 / NUMA 架构  
> **服务器架构**：主从 Reactor 多线程（Main Reactor accept + N 个 Sub Reactor/Worker 处理 IO）  
> **核心优化**：全局时间轮 → 局部时间轮（10.0 版，消除全局锁竞争）

---

## 一、测试参数说明

```bash
# 通用命令格式
wrk -t <客户端线程数> -c <并发连接数> -d 10s -R <目标RPS> -L --timeout=5s http://127.0.0.1:8080/

# 参数说明：
#   -t    wrk2 客户端线程数（模拟并发请求方）
#   -c    保持的 TCP 连接数（长连接模式，一般 = RPS/100）
#   -d    测试持续时间（秒）
#   -R    目标吞吐率（每秒请求数），wrk2 恒定速率模式
#   -L    打印延迟分布统计（HdrHistogram）
#   --timeout  单次请求超时时间
```

| 指标 | 16 线程 | 36 线程 | 差异 | 原因 |

## 七、多线程扩展性分析

| 线程数 | 峰值 QPS（P99<50ms） | 相对 4 线程提升 | 理论提升 | 扩展性效率 |
|---|---|---|---|---|
| 4 | ~20 万 | 1.0x | 1.0x | 100% |
| 16 | ~65 万 | **3.25x** | 4.0x | **81%** |
| 36 | ~35 万 | 1.75x | 9.0x | **19%** |

> **扩展性效率** = 实际提升 / 理论提升  
> 16 线程效率 81%，表现优秀；36 线程效率仅 19%，因主线程 accept 单点成为严重瓶颈。

### 扩展性损耗原因

1. **主线程瓶颈**：accept + dispatch 仍然是单线程，所有新连接都经过它
2. **跨线程通知开销**：主线程分配连接到 Worker 需要 `write(notify_fd_)` 通知
3. **Worker::mutex_ 竞争**：`addConnection` 仍需主线程加锁
4. **NUMA 跨节点访问**：36 线程分布在两颗 CPU 上，跨节点访问内存延迟翻倍
5. **网卡中断集中**：默认网卡硬中断只落在一个 CPU 核上

## 八、优化技术总结

### 8.1 全局时间轮 → 局部时间轮

**优化前（全局单例）：**
```
Worker[0] ──┐
Worker[1] ──┤
Worker[2] ──┼──► 全局 TimerWheel::instance()  ← 唯一 mutex_ 串行点
Worker[3] ──┤     后台 tick 线程
  ...      ──┘     超时回调跨 Worker 查找 (O(N))
Worker[15] ─┘
```

**优化后（局部实例）：**
```
Worker[0] → timer_wheel_ (无锁!) → tick() 在 loop() 本地驱动
Worker[1] → timer_wheel_ (无锁!) → tick() 在 loop() 本地驱动
Worker[2] → timer_wheel_ (无锁!) → tick() 在 loop() 本地驱动
  ...
Worker[15] → timer_wheel_ (无锁!) → tick() 在 loop() 本地驱动
```

### 8.2 关键改动文件

| 文件 | 改动内容 |
|---|---|
| `timer_wheel.h/.cpp` | 移除单例、mutex、后台线程；新增 `tick()` 返回过期 fd 列表 |
| `worker.h/.cpp` | Worker 持有独立 `TimerWheel timer_wheel_`；`loop()` 中每秒调 `tick()` |
| `connection.h` | 移除 `timewheel_refresh_slot` 字段 |
| `connection_pool.cpp` | `softReset` 中移除 `timewheel_refresh_slot` 重置 |
| `threadpool.h/cpp` | 移除 `tryCloseConnectionOnAnyWorker()` 跨线程查找 |
| `server.cpp` | 移除 TimerWheel 回调注册 |
| `main.cpp` | 移除全局 TimerWheel init/shutdown |

### 8.3 核心设计原则

1. **消除共享**：每个 Worker 独立时间轮，无全局锁竞争
2. **锁外回调**：`tick()` 返回过期 fd 列表，回调在锁外执行，防死锁
3. **自驱动**：`tick()` 由 Worker 的 `loop()` 中 `epoll_wait` 返回后检查 1 秒间隔触发
4. **幂等安全**：`removeConnection` 对已过期 fd 做 no-op
5. **精简数据流**：超时从"回调→线程池→轮询 N 个 Worker→查找→关闭"简化为"tick→直接关闭"

### 8.4 后续优化方向（多 Reactor 架构）

当前瓶颈是**主线程 accept 单点**，升级为 SO_REUSEPORT 多 Reactor 架构可解决：

| 优化阶段 | 改动内容 | 预估峰值 QPS | 瓶颈消除 |
|---|---|---|---|
| **阶段1** | SO_REUSEPORT + 每 Worker 自己 accept | **120~150 万** | 主线程 accept 瓶颈 |
| **阶段2** | + NUMA 绑定（Worker 绑本地 CPU 节点） | **160~200 万** | NUMA 跨节点延迟 |
| **阶段3** | + 网卡 RPS/RFS/XPS | **200~280 万** | 网卡中断集中 |
| **阶段4** | + 批量 accept + io_uring | **300~400 万** | 系统调用次数 |

## 九、结论

| 结论 | 数据支撑 |
|---|---|
| 局部时间轮彻底解决了全局锁竞争 | 16 线程 QPS 从 6 万 → 65 万（**10.8 倍提升**） |
| 多线程实现线性扩展（至 16 线程） | 4→16 线程 QPS 提升 3.25 倍，效率 81% |
| 16 线程是当前架构的最优配置 | 稳定 QPS 50 万，峰值 77 万，P99 < 20ms |
| 36 线程性能下降因主线程瓶颈 | 扩展性效率仅 19%，accept 单点成为制约 |
| 延迟稳定性优秀 | 3 轮测试数据波动 < 1%（300K-500K RPS 区间） |
| 下一步应升级为多 Reactor | 消除主线程 accept 单点，预估可突破 120 万 QPS |
